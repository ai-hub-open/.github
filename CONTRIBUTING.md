# Как внести вклад

Спасибо, что хотите доработать инструменты. Каждое принятое исправление экономит время всем, кто ими работает, а ваше имя остаётся в истории изменений и в авторах.

Вклад кодом не обязателен: скиллы — это методология, написанная по-русски. Разбор ошибки агента с примером, уточнение инструкции в SKILL.md, пример из вашей практики — полноценный вклад, и часто более ценный, чем правка кода.

## Что принимаем

- Исправления ошибок и уточнения документации.
- Поддержку новых полей и операций API площадок — со ссылкой на официальную документацию площадки.
- Улучшения правил безопасности (черновики, подтверждения, журнал) — это ядро проекта, такие правки проверяем внимательнее всего.
- Новые скиллы и мосты — сначала откройте Issue с предложением, чтобы не делать работу впустую: обсудим, впишется ли инструмент в организацию. Организация не ограничивается рекламными площадками: принимаем инструменты под любые задачи маркетолога и бизнеса, которые агент может взять на себя.

## Что не принимаем

- Правки, ослабляющие правила безопасности: снятие черновиков и пауз, включение удаления объектов, запись без подтверждения. Такие PR мы закрываем и объясняем почему.
- Возможности, которых нет в API площадки, и описания, обещающие больше, чем делает код: мы сверяем документацию с кодом.

## Ветки

В каждом репозитории организации две постоянные ветки:

| Ветка | Что это | Можно ли пушить напрямую |
|---|---|---|
| `main` | Стабильная. То, что люди устанавливают себе. | **Нет.** Ветка защищена, изменения только через Pull Request |
| `dev` | Рабочая. Сюда приходят все изменения и здесь они «отлёживаются» | Да, участникам организации |

Рабочие ветки под конкретную задачу создавайте **от `dev`**, а не от `main`. Ветка от `main` рано или поздно упрётся в конфликт: `dev` уже ушёл вперёд, и ваш PR потянет за собой чужие изменения.

Именуйте по смыслу правки: `fix/pdf-cyrillic`, `feat/lookalike-audiences`, `docs/install-macos`.

## Порядок для участников организации

```
git checkout dev
git pull
git checkout -b fix/короткое-описание
```

Внесите изменения. Документация — по-русски; названия инструментов и полей API — как в оригинале площадки. Если изменили возможности инструмента — обновите README, включая раздел об ограничениях.

```
git commit -s -m "fix: что и почему"
git push -u origin fix/короткое-описание
```

Дальше — Pull Request **в `dev`** (не в `main`). Мелкую правку можно закоммитить прямо в `dev`, но PR предпочтительнее: он оставляет обсуждение в истории.

## Порядок для внешних авторов

Прав на запись в репозиторий у вас нет — работаем через форк.

**1. Форк.** Нажмите Fork и **снимите галочку «Copy the default branch only»**. По умолчанию она включена, и в форк уедет только `main` — ветки `dev`, от которой нужно ответвляться, там не окажется.

Если форк уже сделан без неё, ничего страшного — `dev` можно дотянуть из исходного репозитория:

```
git remote add upstream https://github.com/ai-hub-open/ИМЯ-РЕПОЗИТОРИЯ.git
git fetch upstream dev
git checkout -b fix/описание upstream/dev
```

**2. Ветка от `dev`.** Если `dev` в форке есть:

```
git checkout dev
git checkout -b fix/описание
```

**3. Изменения и подпись.** Внесите правки, подпишите коммиты (DCO, см. ниже), запушьте ветку в свой форк.

**4. Pull Request.** Открывайте по шаблону и **обязательно переключите base-ветку на `dev`**. GitHub подставляет `main` по умолчанию — с ней PR не примут, придётся переоткрывать. В форме создания PR base-ветка выбирается слева, рядом с надписью `base:`.

Отдельно про правки, затрагивающие безопасность (подтверждения, черновики, работа с ключами): такие PR проверяются отдельным порядком и проходят дольше. Это не недоверие, а цена ошибки — инструменты работают с живыми бюджетами.

## Защита ветки main

`main` защищена настройками GitHub. Что это значит на практике:

- Прямой `git push` в `main` отклоняется — **у всех, включая администраторов организации**. Ответ сервера выглядит так:
  ```
  remote: error: GH006: Protected branch update failed for refs/heads/main.
  remote: - Changes must be made through a pull request.
  ```
  Это не сбой доступа и не повод искать обходной путь: изменение нужно провести через Pull Request.
- `git push --force` в `main` запрещён, удалить ветку нельзя.
- Обязательных апрувов нет — свой PR можно смержить самому. Правило существует не ради бюрократии, а чтобы ни одно изменение не попадало в стабильную ветку в обход обсуждения и проверок.

Если вы уже наделали коммитов локально в `main` — не удаляйте их, перенесите в нормальную ветку:

```
git branch fix/моя-правка
git reset --hard origin/main
git checkout fix/моя-правка
```

## Слияние dev в main

Выпуск стабильной версии — это Pull Request из `dev` в `main`.

Мержить нужно **обычным merge-коммитом**, не squash и не rebase. При squash в `main` попадает новый коммит с другим хешем, `dev` и `main` расходятся, и следующий PR потащит за собой уже слитые изменения плюс конфликты. Squash хорош для короткоживущих веток задач, для долгоживущей `dev` — нет.

После слияния ветку `dev` **не удаляйте** — GitHub предложит кнопку «Delete branch», её здесь жать не надо. И подтяните `main` обратно в `dev`, чтобы ветки не разъезжались:

```
git checkout dev && git pull && git merge origin/main && git push
```

## Чего не должно попасть в историю

Репозитории публичные, и коммит виден сразу всем. Удалить что-либо из публичной истории практически невозможно — переписывание истории ломает форки и клоны, а сам факт утечки к тому моменту уже случился. Поэтому до коммита проверьте, что в изменениях нет:

- ключей, токенов, паролей — включая «отозванные» и «тестовые»;
- файлов `.env`, `credentials.json`, приватных ключей (`*.pem`, `*.key`, `id_rsa`);
- внутренних адресов, ссылок на внутренние документы и трекеры;
- данных клиентов: выгрузок статистики, идентификаторов кабинетов, CRM-списков.

Ключи хранятся вне репозитория: у скиллов — в домашней папке пользователя, у мостов — в переменных окружения или конфиге агентной среды. Внутри репозитория место только шаблонам вроде `.env.example` — с пустыми значениями.

Если ключ всё-таки попал в коммит: **сразу отзовите его на стороне сервиса** и напишите на ai-hub-open@proton.me. Отзыв важнее вычистки истории — ключ считается скомпрометированным с момента публикации.

## DCO — подпись вклада

Мы используем Developer Certificate of Origin: строка `Signed-off-by: Имя <email>` в каждом коммите подтверждает, что у вас есть право передать этот код под лицензией репозитория (Apache-2.0). Подпись добавляется командой:

```
git commit -s
```

Отдельных договоров подписывать не нужно.

## Имена новых репозиториев

Скилл называется по роли агента (`marketing-strategist`), мост — по площадке с суффиксом `-mcp` (`yandex-direct-mcp`).
